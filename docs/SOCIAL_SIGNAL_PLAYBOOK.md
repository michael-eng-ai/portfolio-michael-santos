# Social Signal Playbook

## Purpose

Separate **site long-form** from **social signal posts**, so LinkedIn and X stop looking like automated article dumps with AI covers — and start looking like curated, human posts with real-world proof visuals (GitHub README, product UI, docs, dashboards).

This playbook complements:

- `CONTENT_CHANNEL_SYSTEM.md` (channel roles)
- `AUTHORITY_PROFILE_PLAYBOOK.md` (profile alignment)
- `SOCIAL_API_SETUP.md` (credentials / publish mechanics)

It does **not** change publish tokens or auto-publish behavior.

---

## Why the DocuSeal-style example works

Pattern:

1. **Human hook with stakes** — curiosity + money / industry / failure risk in the first line  
   Example shape: *“Alguém no GitHub desafiou uma indústria de US$ 10 bilhões.”*
2. **Name the thing fast** — what it is, in one breath (DocuSeal = open-source e-sign).
3. **Real proof visual** — screenshot of the actual GitHub README / product UI, not decorative AI art.
4. **Implicit credibility** — GitHub chrome (tabs, badges, license) signals “this exists in the world right now.”

For Michael’s brand, the same pattern applies **only inside the niche**: data engineering, AI platforms, pipelines, observability, lakehouse, RAG/ops — not random viral SaaS.

## Content types (keep them distinct)

| Type | Job | Voice | Visual |
|------|-----|-------|--------|
| **A) Site article** | SEO + authority deep dive | Technical / executive, scannable | Gemini / editorial cover OK for hero + OG |
| **B) Social signal** | Feed attention + credibility | Curiosity + stakes + one insight | **Real screenshot only** |
| **C) Article promo** (optional) | Drive to site after a signal or weekly | Shorter bridge post | Prefer screenshot of *your* architecture/repo; AI cover only as last resort |

Today’s automation (`content:linkedin` / `content:x`) mostly produces **C disguised as B**: hooks from SEO excerpts + `mediaPath` pointing at AI article covers under `public/images/articles/`.

**Target mix:** more **B**, keep **A**, use **C** sparingly (≈1× per article launch).

---

## Cadence (recommended)

- **3 social signals / week** (LinkedIn primary; X can mirror a tighter cut of 1–2 of them)
- **1 long-form site article / week** (existing daily/weekly article pipeline can stay; do not auto-promote every article to feed with AI cover)
- **Optional:** 1 “project proof” signal / week from *your* repos (architecture diagram, dashboard, PR, README) to reinforce michael.business / GitHub authority

Hard rule: never auto-publish a signal without `status: approved`.

## Image rules

### Do (social feed)

- GitHub README / repo header screenshot (stars, license, hero markdown)
- Product docs or official UI of a tool **you are commenting on**
- Architecture / DAG / dashboard from **your** projects
- Crop of a credible news/docs page (OG or article header) when the story *is* the news
- Store under e.g. `public/images/social/<slug>.png` and set draft `mediaPath` + `mediaSource: "screenshot"`

### Don’t (social feed)

- Gemini decorative covers from `lib/image-gen.ts` / `content:backfill:covers`
- Generic stock / abstract “data pipes” art as the main visual
- Over-branded Canva templates that scream “content machine”
- Fake UI mockups generated by AI

### OK elsewhere

- AI covers remain fine for **site article hero + Open Graph** (`public/images/articles/`)
- Site OG scrape as LinkedIn ARTICLE fallback when there is no screenshot (see `lib/linkedin.ts`)

## Topic selection (stay on-brand)

Pull candidates from existing stack, then **human-pick 3**:

| Source | Script / artifact | Use for signals when… |
|--------|-------------------|------------------------|
| Daily trend briefing | `pnpm content:daily:briefing` | Market pressure maps to data/AI platform decisions |
| News sync + editorial | `content:sync:news`, `content:enrich:news` | You have a sharp take, not a rewrite of the headline |
| Your GitHub projects | `content:sync:github`, `content/projects/*` | You can show *your* proof screenshot |
| Niche GitHub trending / releases | Manual or future scraper | Tool is relevant to DE/AI ops (dbt, Kafka, Spark, pgvector, Airflow, MCP, etc.) |

Reject if: no DE/AI angle, no stake, or no real URL you can screenshot.

## Editorial workflow (step-by-step)

### 1. Intake (daily, 10 min)

From briefing / news / GitHub, shortlist 1–3 candidates with:

- stake (cost, risk, latency, adoption gap, open-source vs incumbents)
- proof URL (repo, docs, dashboard, your article/project)
- niche fit (one sentence: why *you* should post this)

### 2. Capture media (5–10 min)

Prefer Playwright (or browser DevTools) full-page or viewport capture of the proof URL.

Suggested conventions:

- Path: `public/images/social/<yyyy-mm-dd>-<short-slug>.png`
- Draft fields: `mediaPath`, `mediaSource: "screenshot"`, `urls.proof` = captured URL
- Optional later: `scripts/capture-social-screenshot.ts` (Playwright) — not required to start

Firecrawl / crawl is useful for **text context**, not as a substitute for a clean feed screenshot.

### 3. Write the signal (AI-assisted, human-edited)

Structure (LinkedIn):

1. **Hook** — stakes + curiosity (PT or EN; match audience). Never paste the SEO title.
2. **Name + frame** — what it is + why data/AI engineers should care.
3. **One insight** — your angle (tradeoff, failure mode, pattern).
4. **CTA soft** — site article, your repo, or “curious how you’d implement this” — not hard sell.

X: same hook, shorter body, one proof URL; thread only if needed.

Prompt constraints for any LLM helper:

- Forbidden: “Learn how…”, “Veja como…”, “In this article…”, title paraphrase
- Required: first line creates tension; second line names the subject; body adds *your* DE/AI lens
- Language: PT-BR for LinkedIn BR audience; EN when the signal is global-tooling

### 4. Draft file (repo)

Prefer a dedicated draft (new) over regenerating article promos:

- `content/linkedin/signal-<slug>.json`
- `content/x/signal-<slug>.json` (optional mirror)

Use `sourceType: "signal"` with `pnpm content:signals` (or hand-authored `signal-*.json`). Article/project promo drafts remain a separate lane.

Minimum fields today:

- `status: "draft"` → human sets `"approved"` → publish job / workflow
- `mediaPath` → screenshot path
- `mediaSource` → `"screenshot"` | `"ai"` | `"none"` (schema support)
- `locales.*.hook|body|cta`
- `urls.en` / `urls.pt` / `urls.proof`

### 5. Human-in-the-loop

Checklist before `approved`:

- [ ] Hook is not SEO-title clone
- [ ] Visual is a real screenshot (not AI cover)
- [ ] Niche fit is obvious in ≤2 lines
- [ ] Proof URL works
- [ ] No secrets / internal UI
- [ ] Does not feel like “bot posted my blog again”

Publish only approved drafts (`content:publish:linkedin`, social-distribution workflow, or manual). Do not widen auto-publish to all drafts.

### 6. Site article (separate track)

Keep `generateDailyArticle` / Claude article path for long-form. Gemini covers stay on **site**. Social signal may *reference* the article later; do not treat article generation as “also generate LinkedIn visual.”

## What to change per channel

### LinkedIn

- Primary home for **signal** posts (hook + screenshot IMAGE share)
- Stop defaulting `mediaPath` to AI article covers for feed distribution
- Use IMAGE upload path in `lib/linkedin.ts` / `lib/social-media.ts` with screenshot files
- Article promo: at most one post per launch, preferably with repo/UI proof, not abstract cover

### X

- Shorter rewrite of the best LinkedIn signals (not 1:1 copy)
- Attach the same screenshot when it still reads at small size; otherwise crop tighter
- News tweets (`post-news-to-x.ts`) can stay as a separate lane — still prefer real OG/source visual over AI

### Site articles

- Unchanged SEO / technical voice
- AI covers + OG images OK
- Do not weaken long-form to chase viral hooks; pull hooks *from* articles into signals when useful

## Prompt pack (hooks)

### System (short)

You write LinkedIn/X signals for a senior data engineer / AI platforms consultant (michael.business).  
Output PT-BR or EN as requested. First line = stakes + curiosity. Never invent metrics. Never use SEO titles. Visual will be a real screenshot; do not describe AI art.

### User template

```text
Subject: <tool / repo / news>
Proof URL: <github or docs>
Niche angle (data/AI): <one sentence>
Stake: <cost | risk | latency | adoption | open-source disruption>
Locale: pt|en
Channel: linkedin|x

Return JSON:
{
  "hook": "...",
  "body": "...",
  "cta": "..."
}
```

### Good hook shapes

- “Alguém no GitHub desafiou [mercado / default / vendor lock-in] de [X].”
- “A maioria ainda paga [Y] por um problema que [tool] resolve em open source.”
- “[Incidente / pattern]: o custo não está no modelo — está no [pipeline / retrieval / orchestration].”

### Bad hook shapes (reject)

- “Learn how to tune pgvector HNSW…”
- “New article on my blog about…”
- “Excited to share…”

## Anti-automation tells (checklist)

Posts look automated when:

- Same cover style every day (AI navy abstract)
- Hook = article title / “Learn how”
- Always the same CTA paragraph about GitHub proof
- Publishing cadence = every merge, no curation

Posts look curated when:

- Visual is a specific real page
- Hook could only fit that story
- You add one opinionated DE/AI sentence
- Volume is capped and approved

---

## Guardrails

- Do not paste secrets into drafts or screenshots.
- Do not publish from this playbook alone — approval required.
- Fair use: screenshot for commentary; link to source; don’t imply endorsement.
- Stay inside authority pillars: business pressure, operational proof, consulting judgment.
